01 / Project intent

More than CRUD.
A system of invariants.

The build models the parts that make inventory software difficult: quantities that must never drift, documents that change state, actions that require authority, and operations that need an explanation after the fact.

A

Balances answer “how much?”

warehouse_stocks keeps fast current quantities scoped by product and warehouse.

B

The ledger answers “why?”

Every successful stock mutation records its type, quantity, actor, document, and warehouse context.

C

Services protect both.

Database transactions keep document state, balances, movements, and audit history consistent.

02 / Domain workflows

Business rules live in the transitions.

Each workflow is permission-gated, validated at the boundary, and committed atomically. Invalid state changes are rejected before inventory or audit records can drift.

03 / Architecture

Boundaries that keep change local.

A conventional Laravel structure is used deliberately: the framework handles delivery concerns while focused services own cross-model workflows and consistency rules.

HTTP boundary

Routes → Form Requests → Controllers

Middleware authorizes access. Form Requests validate intent. Controllers translate web actions into service calls.

  • Custom RBAC middleware
  • Laravel Gates + Blade checks
  • Thin controller actions
Domain boundary

Workflow services

Stock, purchasing, reporting, dashboard, and audit concerns are separated into focused service classes.

  • Explicit state rules
  • Transactional mutations
  • Reusable report queries
Persistence boundary

Eloquent models & relational constraints

Normalized master data, transactional documents, stock balances, immutable movement history, and audit records.

  • Restrict / cascade / null delete rules
  • Soft-deleted master data
  • Decimal money + quantities

Core consistency contract

No successful stock change exists without a balance update and a matching movement record.

All-or-nothing database transaction
